# 我给自己造了一份前端项目模板


**Github链接**：[XD-xiao/vueTemplate: vue项目初始模板](https://github.com/XD-xiao/vueTemplate)


如果你写过几个后台页面，大概经历过这样的循环：

新项目立项 → 建仓库 → 装 Element Plus → 写登录页 → 封一层 axios → 想起来还得存 token → 想起路由要拦一下 → 想不起上次权限是怎么判的，翻旧项目复制粘贴 → 改了一堆地方才能跑起来。

前几次还好，做多了就有点烦。更烦的是，复制来的代码里总带着上一个项目的残留：接口地址写死在某处、权限点名字对不上后端、样式变量藏在八百里外的文件里。半年后再回来看这个项目，还得重新考古一遍。

所以我花了点时间，把这一套"老几样"整理成了一份模板项目。**开新项目时拉下来，改几个配置就能直接开工。**

它不是框架，也不是脚手架工具，就是一份我自己在用的、把常用能力提前装好的 Vue 3 工程。

## 先说清楚它是什么

一句话：**一个通用后台前端模板，装好了基础设施，但不含任何业务代码。**

除了用来验证功能的自测页面，模板里没有"用户管理""订单列表"这种东西——那些每个项目都不一样，塞进去只会变成负担。它负责的是每个项目都要做、但每次都懒得重写的那部分：

| 你本来要自己做的事 | 模板里已经有了 |
| --- | --- |
| 接口地址写哪、换环境怎么办 | 运行时配置，改一个文件，不用重新打包 |
| token 存哪、怎么持久化 | Pinia + 持久化插件，key 都带好前缀 |
| 没登录跳登录页、没权限跳 403 | 路由全局守卫，顺序都排好了 |
| 请求解包、token 过期自动续期 | axios 封装，401 自动刷新并重试原请求 |
| 按钮按权限显示/隐藏/禁用 | `v-permission` 指令，一行搞定 |
| 权限点散落各处、后端对不上 | 权限清单 + 构建期审计 |
| 换主题色、切暗色、改组件尺寸 | 全局外观配置，刷新还记得你的选择 |

技术栈都是熟脸：Vue 3（`<script setup>`）、Vite、Element Plus、Pinia、Vue Router、axios。没有冷门依赖，别人接手也不用先学一套新东西。

## 几个我自己最满意的设计

### 部署完还能改接口地址

以前换环境要么改代码重新打包，要么在构建时塞一堆环境变量。模板用的是最朴素的办法：根目录放一个 `public/config.js`，打包后就是 `dist/config.js`，部署上去直接用记事本改：

```js
window.__APP_CONFIG__ = {
  API_BASE_URL: 'http://localhost:8080'
}
```

代码里读不到就退回 `/api`，不会因为忘配就崩掉。

当然，这个文件是公开的，**永远不要往里面放密钥**——这是我写在 README 里的第一条警告。

### 权限点会自己查漏补缺

这是模板里我最喜欢的一块，也是踩坑最多的部分。

麻烦在于：代码里写了个 `user:demo:add`，但登记表里忘了加；或者登记表里有一堆权限点，代码早就删了，谁也不敢清理，怕删错。时间一长，前后端的权限表就谁也不认识谁了。

模板的做法是把 `src/permissions.js` 定成**唯一维护入口**，然后让构建工具去当监工：

- `npm run dev` 启动时，扫描源码里的权限点，和清单比对，输出"使用 N 个 / 已登记 M 个"。**没登记的**会告警并给出`文件:行号`；**登记了但代码里没用的**也会告诉你——这样死权限能被揪出来，而不是烂在那。
- 开发时保存文件会重新审计，只报问题项，不刷屏。
- `npm run build` 时，只要还有没登记的权限点，**直接构建失败**。宁可打包不出来，也不要上线之后才发现某个按钮谁都点不了。
- 构建成功会顺手导出 `dist/permissions.json`，格式正好能给后端初始化权限表：

```json
[
  { "permName": "权限测试页", "permType": 1, "permKey": "user:demo:page" },
  { "permName": "演示-新增", "permType": 2, "permKey": "user:demo:add" }
]
```

命名规范也跟着定死了：`模块:实体:操作`，至少三段、全小写。格式不对或者重复登记，直接就报错——早报错比晚报错便宜。

扫描规则也做了防误判：只认带引号的完整权限点（所以 `localhost:8080` 这种两段串不会被误伤），跳过注释行，也跳过清单文件自身（否则登记项会被当成"已使用"，死权限永远查不出来）。

### 权限控制就是一行指令

写页面的时候，不用再 `v-if="hasPermission('xxx')"` 到处翻 store：

```vue
<!-- 有权限才显示 -->
<el-button v-permission="'user:demo:add'">新增</el-button>

<!-- 满足任意一个就显示 -->
<el-button v-permission="['user:demo:add', 'user:demo:edit']">编辑</el-button>

<!-- 必须全部满足 -->
<el-button v-permission.all="['a:b:c', 'd:e:f']">操作</el-button>

<!-- 没权限时置灰，而不是"消失"——表单类元素更友好 -->
<el-button v-permission.disable="'user:demo:delete'">删除</el-button>
```

内部用 `watchEffect` 订阅权限仓库，**登录、登出、刷新 token 之后会实时重算**，不用手动刷新页面。隐藏用的是 `display: none` 而不是销毁 DOM，所以权限变了能立刻恢复回来。

还有个小细节：开发期如果你写了一个没登记过的权限点，控制台会告警——不用等到构建失败那一刻。

### 主题色是算出来的，不是写死的

外观这块我做得比较细。主题模式（亮色/暗色/跟随系统）、组件尺寸、主题色都收在一个 store 里，改完全局即时生效，而且刷新还记得。

主题色只需要给一个 `#RRGGBB`，浅色和深色变体是算出来的——算法和 Element Plus 自己的 SCSS 规则一致，所以按钮的 hover、禁用、浅底色调都能跟着一起变，不会出现"主色变了但某个状态还是蓝的"这种尴尬。

另外 `index.html` 里放了一小段内联脚本，在页面渲染之前就把主题套上。如果你也用过暗色模式，应该见过那种"先闪一下白再变黑"的体验——这段脚本就是专门治它的。

## 想用的话，三步

如果你也有类似的需求，可以直接拿去用：

```bash
npm install
npm run dev      # 打开 http://localhost:5173，首页就是自测索引
npm run build    # 构建，顺便导出权限清单
```

> 需要 Node.js `^20.19.0 || >=22.12.0`。

启动后的首页是一个自测索引，能逐项验证运行时配置、主题、设备信息、Element Plus、权限守卫是否正常。**建议先照着点一遍**，心里有数了再开始删东西。

改造成自己的项目，按 README 里那份清单走就行，大致是：改 `package.json` 的名字、改 `constants.js` 里的 `APP_TITLE` 和接口前缀、改 `public/config.js` 的接口地址、删掉 `src/views/test/` 和对应路由、重写权限清单、把占位登录页换成真实登录。

## 也说说不完美的地方

我不想把它说成"什么都能干"。这一版有几个明确的边界，用之前值得知道：

- **没有 dev 代理**。`config.js` 指向绝对地址，开发时跨域靠后端配 CORS。真要本地代理，自己在 `vite.config.js` 里加 `server.proxy` 更省事。
- **没有 layout 和菜单**。侧边栏、顶栏、面包屑、按权限动态注册路由并派生菜单，这些都没内置。不是不想做，是每个项目的后台长什么样差别太大，硬猜不如留白。
- **Access Token 存在 localStorage**，有 XSS 风险。安全要求高的项目，建议改成只放内存，靠 HttpOnly Cookie 刷新——README 里写了改法。

这些我都写在 README 的「已知限制」里了。**把自己没做的地方写明白，比假装都做了要诚实**——毕竟模板的意义是省事，不是让人踩坑。

## 最后

这份模板省下的，其实不是第一次搭项目的那两小时，而是后面每一次的"这个项目当时是怎么弄的来着"。

把约定写进代码里、让工具在构建时替你检查、把踩过的坑记在 README 的"已知限制"里——这些事情做一次，之后每个项目都受益。这大概是我做这份模板最大的收获。

如果你也想给自己攒一份，欢迎参考；如果你已经有自己的做法，也很想听听你是怎么处理权限清单这件事的。
